# Architecture

The app is C (gnu99), built with [VitaSDK](https://vitasdk.org). The interface is drawn with vita2d;
the streaming protocol is [moonlight-common-c](https://github.com/moonlight-stream/moonlight-common-c);
the requests to the PC (server info, pairing, game list, launch) are libgamestream, from Moonlight
Embedded.

## Threads and cores

The Vita gives applications three CPU cores. With *Spread work over the cores* on (default), the
streaming threads are placed as below (dubleyu/vita-moonlight-relay's split); off, the system places
them. Priorities: smaller is more urgent; 64 is the highest for applications, 160 the default.

| Thread | Created by | Priority | Core | Role |
|---|---|---|---|---|
| main | system | default | any | menus; waits while a stream runs |
| `VideoRecv`, `AudioRecv` | moonlight-common-c | 64 | 1 | read the UDP sockets, FEC, reorder window |
| `ControlRecv`, `VideoPing`, `AudioPing` | moonlight-common-c | default | 1 | control channel and keep-alives |
| `VideoDec` | moonlight-common-c | 64 | 2 | hardware H.264 decode into a frame slot (`vita_submit_decode_unit`) |
| `AudioDec` | moonlight-common-c | 64 | 2 | Opus decode, classic output |
| `vita_audio_out` | audio/vita.c | 64 | 2 | low-latency audio output (5.33 ms blocks) |
| `vid_display` | video/vita.c | 64 | 0 | picks the frame and draws it (all modes but *Original*) |
| `vid_vblank` | video/vita.c | 64 | 0 | screen timing for *Lowest latency* and *Original* |
| input (pthread) | input/vita.c | 96 | 0 | buttons, touch, sends controller events |
| `InputSend` | moonlight-common-c | default | 0 | sends input packets |
| motion, stats (pthreads) | input/motion.c, stream_stats.c | default | 0 | gyro/accelerometer, statistics once a second |
| `frame_pacer` | video/vita.c | 0, as in the original code | any | original frame pacer: in direct display mode with *Frame pacer* on, drops frames above the stream rate |
| `boxart` (pthread) | gui/boxart.c | 176 | any | cover art download, paused while streaming |
| `log_writer` | log.c | 191 | any | writes the log ring to the memory card, once a second or sooner |
| `startup` | gui/splash.c | default | any | at start-up only: the steps of `main.c` (network, controls, PCs) while the menu thread renders the fonts |
| `decoder_probe` | gui/ui_settings.c | 191 | any | from the start-up: which stream sizes the decoder accepts; Settings and the start of a stream wait for its end |

moonlight-common-c calls `LiVitaThreadStarted()` (patch 0003) from each thread it starts, which sets
the priority and core by thread name (`src/thread_policy.c`). Threads that call into
moonlight-common-c or the HTTP client are pthreads: their locks are pthread ones, and
dubleyu/vita-moonlight-relay saw `sem_timedwait` crash in kernel threads.

## Stream states

`src/connection.c`: `DISCONNECTED → READY → PAIRED → CONNECTED ⇄ MINIMIZED (paused)`. A pause
(START + L + R) stops input, video and audio output but keeps the connection; the menus then own the
screen. The end of a stream can be reported by moonlight-common-c on its own thread (the PC quit the
game) while the menus end it too: `connection_connection_terminated()` is serialised by a lock so
that `LiStopConnection()` runs once.

Resuming checks whether a setting that only applies at stream start was changed during the pause
(resolution, bitrate, display mode, audio mode, colour decoding, reorder wait, cores...) and offers to
restart the stream; the game keeps running on the PC.

A stream that ends while it runs with an error that means a lost link (time-outs, socket errors:
`reconnect_after_error()` in `src/reconnect.h`) is marked lost by `connection.c`. The menu thread, which
waits in `ui_launch_app()` while the stream runs, then shows "Connection lost", waits for the Wi-Fi
(`sceNetCtlInetGetState`) and starts the stream of the same game again every 3 s for a minute; the PC
resumes the game it kept running. An end by the PC or the user (`ML_ERROR_GRACEFUL_TERMINATION`), or a
problem on the PC that a new stream would meet again (capture, DRM, picture conversion), is not
reconnected, nor is a stream lost during the pause. Three streams in a row lost within 20 s of starting
stop the reconnection, and so does a game closed on the PC meanwhile (read with `gs_update_status()`
after a refused try).

What runs on the PC (`server.currentGame`) decides between *Play* and *Resume*, and between a
`launch` and a `resume` request. It is read again from the PC (`gs_update_status()`) each time the
library opens, and recorded by `gs_start_app()` only once the PC has accepted the request: Sunshine
refuses inside a normal answer (status 400 or 503 in the XML), which libgamestream used to take for an
acceptance. A session that is only *ready* (a PC just opened) is marked *paired* by `ui_launch_app()`
itself. These paths are replayed on a PC by the preview's journeys (`docs/TESTING.md`).

Threads that are not the stream's: the home screen's PC detection (`src/check_host.c`, `hostscan`) and
the network search (`src/gui/ui_device.c`, `mdns`) both read mDNS answers with
`third_party/mdnsniff`, so one runs at a time; each is stopped by a flag it checks at every step,
waited for and deleted. The detection reads the list of PCs under `devices_lock()`, which every change
of the list takes as well. It asks the network for the PCs (mDNS) before listening for each one: the
PCs answer each question once. With the Away connection it also tries each PC at its home address,
then at its Internet address (a name looked up once per scan); at home, a PC silent there is tried at
its Internet address too. At home it has the box's public address asked (STUN) at most every 10
minutes, in a short thread of its own (a slow name server must not hold the scan), kept under the
same lock; the menus' thread gives it to the PCs and saves them. The PS button is locked and unlocked only by the input thread.

The in-game quick menu (`src/gui/quickmenu.c`) lives inside the stream: the input thread calls
`quickmenu_handle_input()` with each sample before anything is sent to the PC, which opens the menu on
L + R + SELECT, moves in it and carries out the action (statistics, keyboard, `connection_minimize()`
for the pause; the quit is a request that the menu thread carries out once the stream is paused).
While the menu is open, and until every button is released after it closed, the game receives nothing;
what it held is released once. The display thread draws the menu over each frame in `draw_and_flip()`,
from a copy of the state published by the input thread; Sunshine sends at least half the stream's frame
rate even on a still picture, so the menu is redrawn often enough. The decisions are in
`quickmenu_logic.h`, tested on a PC.

Colour themes: `src/gui/theme.c` holds five palettes (`k_themes`); `theme_select()` copies one into
`th_pal`, which the theme-dependent `TH_*` colours read, and loads its background
(`assets/bg_<theme>.png`, a lunar sky drawn by `tools/make_background.py`, one texture per frame like
any picture). Colours that carry a meaning (OK, warning, error, the PlayStation symbols) are the same
in every theme.

Stars of the background: `tools/make_background.py --stars` writes `src/gui/stars.h`, where the stars
of each picture are and, for the moving sky, a ring of stars around the moon (offset from its centre,
size, brightness and the height below which each one sets). With *Twinkling stars*, `theme.c` draws a
soft dot over each still star (`twinkle.h`: when and how much). With *Moving sky*, `theme_select()`
loads the picture without its stars (`assets/bg_<theme>_sky.png`) and `theme.c` draws the ring turned
by one angle, which `orbit_advance()` (`orbit.h`) moves on each frame from where it was, at the speed
and in the direction chosen: changing either does not make the stars jump, and the sky does not move
while no menu is drawn. Only the stars on the screen are drawn (about as many as the still picture
has); the horizon and the top bar are applied where each star is at the time. The dot is one 16 × 16
texture made at start-up.

Type: Inter for the text (Regular up to 16 px, Light above), Poppins, the logo's typeface, for the
titles (22 px and above). Each size has its own vita2d font instance, its glyphs prepared at start-up.

Start-up screen (`src/gui/splash.c`, timeline in `splash_logic.h`): `main.c` reads the settings, then
`splash_run()` brings vita2d up and draws the theme's sky and the moon from the first frame. The steps
of `main.c`, which draw nothing, run on the `startup` thread while the menu thread loads the fonts and
renders their characters a slice per frame (`theme_prewarm()`), so the two loads overlap and the moon
keeps moving. The moon waxes with the loading and becomes the mark (the last picture of
`assets/moon.png`, the same drawing as `logo_mark.png`) once both are done; the mark and the name then
move to where `theme_topbar()` draws them, the rest of the top bar fading in, and the home screen's
first opening fades in under it (`splash_take_intro()`). vita2d calls stay on the menu thread.
Poppins has Latin only: a title with a character it lacks is drawn with an Inter Light instance of the
same size, made the first time one is needed (`face_font()`, with the table
`src/gui/title_font_cover.h` and `text_cover.h`).

The waiting moon (`flash_moon()` in `src/gui/guilib.c`, pictures in `assets/moon.png`, choice of
picture in `moon.h`): a new moon when a PC is contacted or the PC is asked for the game, then one
picture per stage of `LiStartConnection`, drawn by `connection_set_stage_hook()` on the menu thread
before each stage's clock starts, at most one per 50 ms. The moon is full as the video stream starts,
and the menus draw nothing after that stage, since from there the video thread may draw. The log
gives the number of pictures and the time they took (`waiting moon: N pictures drawn in M ms`). The
picture is freed once the full moon is drawn and before each reconnection try, so no texture of the
moon is kept during a game. The names the quick menu draws over the game are prepared on the menu
thread by `quickmenu_set_context()` (`theme_prepare_text()`), so the display thread never rasterises
glyphs or makes a fallback font during play. A
reconnection draws its own screen between tries, the moon filling over the minute of tries; no
picture is drawn during a try.

## Data on the memory card

The data folder is the first that can be created among `ux0:data/vitamoon`, `ux0:vitamoon` and
`uma0:data/vitamoon` (`src/check_dir.c`; the name comes from `src/app_info.h`). On the first start
after the rename, Lune's folder (`ux0:data/lune`, or `ux0:lune`, `uma0:data/lune`) is moved to it, with
`lune.conf` and the logs renamed, so the pairing key and the settings carry over; the folder found
wins over the `key_dir` line of the settings file. It is not shared with
Moonlight, which keeps `ux0:data/moonlight`.

| Path | Content |
|---|---|
| `vitamoon.conf` | settings (`src/config.c`); unknown keys are ignored, out-of-range values reset |
| `<PC name>/` | per PC: client certificate and key, unique ID, `device.ini` (addresses, MAC, paired) |
| `stats/session-<date>.csv`, `.txt` | per stream: one line per second, settings and percentiles |
| `stats/last_<app>.txt` | figures of the last session of each game, for the library (when it was last played, its order, its figures) |
| `favorites.txt` | the library's favourites, one app id per line |
| `boxart/<PC>/<app>.cover` | cover art, resized for the library (192 x 256 RGBA; its corners are made transparent when it is loaded, `src/gui/cover_shape.c`) |
| `logs/vitamoon-<date>.log` | the log of each run, named after its start; the last 30 kept (`src/log.c`, `src/log_files.h`) |

## Log

`src/log.c` writes one file per run, `logs/vitamoon-<YYYYMMDD-HHMMSS>.log` in the data folder (the
start of the run, as the statistics files are stamped), and deletes the oldest beyond 30 runs
(`log_files.h`, which shares its choice with the statistics files' `stats_prune.h`). Up to
1.0.0-beta.11 it wrote `vitamoon.log` and kept `vitamoon.1.log` .. `vitamoon.4.log`; those are moved
into `logs/`, named after their last change, on the first start of 1.0.0. A line reads `14:03:27.512 I stream  started in 412 ms`: local
time (to match the PC's Sunshine log), level (E error, W warning, I information, D detail), subject.

- **Normal log** (always): start-up (version, firmware, model, free memory, battery, Wi-Fi), each PC
  contacted (Sunshine version, GPU, pairing, running game, codecs), each stream (settings, each start
  stage with its time, video, audio and controller set-up, how it ended and after how long),
  reconnections, pause and quick menu, errors, moonlight-common-c's own messages, and one *health* line
  per minute of play (frames, losses, bitrate, ping, PC, decode and display times, sound gaps, Wi-Fi).
  By design a start-up and a ten-minute game come to about a hundred lines (not yet measured on a Vita).
- **Detailed log** (*Settings > General > Detailed log*): every debug line of the code and of the
  HTTP requests (their query, which holds the stream key, is never written).

Callers format the line under a lightweight lock and copy it into a 64 KiB ring (`log_core.c`); the
low-priority `log_writer` thread puts the ring on the card once a second, at once after an error, and
reopens the file if a sleep closed it. No stream thread waits for the memory card. Floods are bounded:
the same line repeated is written once and then counted; each kind of line has a token bucket (a burst,
then a few lines a second; moonlight-common-c's loss messages 3 a second), and the next line written
says how many were left out; a full ring drops whole lines and says so; a file stops at 4 MiB.
