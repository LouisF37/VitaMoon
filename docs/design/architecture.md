# Architecture

The app is C (gnu99), built with [VitaSDK](https://vitasdk.org). The interface is drawn with vita2d;
the streaming protocol is [moonlight-common-c](https://github.com/moonlight-stream/moonlight-common-c);
the requests to the PC (server info, pairing, game list, launch) are libgamestream, from Moonlight
Embedded.

## Source layout

| Folder | Content |
|---|---|
| `src/main.c` | start-up: data folder, log, settings, pairing name, network, then the menus |
| `src/log.c`, `src/log_core.c` | the log: levels, ring, writer thread, budgets (pure part tested on a PC) |
| `src/app_info.h` | name of the app and of its data folder (package identity: top of `CMakeLists.txt`) |
| `src/config.c` | settings file `lune.conf`: defaults, reading, sanitising, writing |
| `src/connection.c` | stream state machine (ready, paired, connected, paused) and moonlight-common-c callbacks |
| `src/video/vita.c` | video renderer: hardware H.264 decoding, frame slots, display thread, display modes |
| `src/video/pacing.c` | *Paced* display timing (pure logic, tested on a PC) |
| `src/video/stream_stats.c` | per-second statistics, overlay, CSV and session summary; `histogram.h` for percentiles |
| `src/audio/vita.c` | Opus decoding and audio output, classic and low-latency (adaptive buffer) |
| `src/input/` | controls: buttons, sticks, front and rear touch, motion, keyboard, shortcuts, mapping files |
| `src/power/vita.c` | clock boost while connecting and streaming, Wi-Fi and Bluetooth settings read from the registry |
| `src/thread_policy.c` | priorities and CPU cores of the streaming threads |
| `src/gui/` | interface: theme, home, library, settings, pairing, dialogs, cover art download |
| `src/i18n.c` | English, French and Spanish texts (generated by `tools/i18n/gen.py`) |
| `src/device.c`, `src/check_host.c` | known PCs and their state (online, offline, address changed) |
| `libgamestream/` | HTTP(S) requests to the PC, pairing, SPS rewrite (`sps.c`), URL encoding |
| `third_party/` | moonlight-common-c (vendored, patched), ENet, inih, h264bitstream, libuuid, mDNS sniffer |
| `tools/` | PC tests, interface preview, translations, developer scripts, Sunshine helpers, LiveArea art |

## Threads and cores

The Vita gives applications three CPU cores. With *Spread work over the cores* on (default), the
streaming threads are placed as below (dubleyu/vita-moonlight-relay's split); off, the system places
them. Priorities: smaller is more urgent; 64 is the highest for applications, 160 the default.

| Thread | Created by | Priority | Core | Role |
|---|---|---|---|---|
| main | system | default | any | menus; waits while a stream runs |
| `VideoRecv`, `AudioRecv` | moonlight-common-c | 64 | 1 | read the UDP sockets, FEC, reorder window |
| `ControlRecv`, `VideoPing`, `AudioPing` | moonlight-common-c | default | 1 | control channel and keep-alives |
| `VideoDec` | moonlight-common-c | 64 | 2 | hardware H.264 decode into a frame slot (`vita_submit_decode_unit`) |
| `AudioDec` | moonlight-common-c | 64 | 2 | Opus decode, classic output |
| `vita_audio_out` | audio/vita.c | 64 | 2 | low-latency audio output (5.33 ms blocks) |
| `vid_display` | video/vita.c | 64 | 0 | picks the frame and draws it (all modes but *Original*) |
| `vid_vblank` | video/vita.c | 64 | 0 | screen timing for *Lowest latency* and *Original* |
| input (pthread) | input/vita.c | 96 | 0 | buttons, touch, sends controller events |
| `InputSend` | moonlight-common-c | default | 0 | sends input packets |
| motion, stats (pthreads) | input/motion.c, stream_stats.c | default | 0 | gyro/accelerometer, statistics once a second |
| `frame_pacer` | video/vita.c | 0, as in the original code | any | original frame pacer: in direct display mode with *Frame pacer* on, drops frames above the stream rate |
| `boxart` (pthread) | gui/boxart.c | 176 | any | cover art download, paused while streaming |
| `log_writer` | log.c | 191 | any | writes the log ring to the memory card, once a second or sooner |

moonlight-common-c calls `LiVitaThreadStarted()` (patch 0003) from each thread it starts, which sets
the priority and core by thread name (`src/thread_policy.c`). Threads that call into
moonlight-common-c or the HTTP client are pthreads: their locks are pthread ones, and
dubleyu/vita-moonlight-relay saw `sem_timedwait` crash in kernel threads.

## Stream states

`src/connection.c`: `DISCONNECTED → READY → PAIRED → CONNECTED ⇄ MINIMIZED (paused)`. A pause
(START + L + R) stops input, video and audio output but keeps the connection; the menus then own the
screen. The end of a stream can be reported by moonlight-common-c on its own thread (the PC quit the
game) while the menus end it too: `connection_connection_terminated()` is serialised by a lock so
that `LiStopConnection()` runs once.

Resuming checks whether a setting that only applies at stream start was changed during the pause
(resolution, bitrate, display mode, audio mode, colour decoding, reorder wait, cores...) and offers to
restart the stream; the game keeps running on the PC.

A stream that ends while it runs with an error that means a lost link (time-outs, socket errors:
`reconnect_after_error()` in `src/reconnect.h`) is marked lost by `connection.c`. The menu thread, which
waits in `ui_launch_app()` while the stream runs, then shows "Connection lost", waits for the Wi-Fi
(`sceNetCtlInetGetState`) and starts the stream of the same game again every 3 s for a minute; the PC
resumes the game it kept running. An end by the PC or the user (`ML_ERROR_GRACEFUL_TERMINATION`), or a
problem on the PC that a new stream would meet again (capture, DRM, picture conversion), is not
reconnected, nor is a stream lost during the pause. Three streams in a row lost within 20 s of starting
stop the reconnection.

The in-game quick menu (`src/gui/quickmenu.c`) lives inside the stream: the input thread calls
`quickmenu_handle_input()` with each sample before anything is sent to the PC, which opens the menu on
L + R + SELECT, moves in it and carries out the action (statistics, keyboard, `connection_minimize()`
for the pause; the quit is a request that the menu thread carries out once the stream is paused).
While the menu is open, and until every button is released after it closed, the game receives nothing;
what it held is released once. The display thread draws the menu over each frame in `draw_and_flip()`,
from a copy of the state published by the input thread; Sunshine sends at least half the stream's frame
rate even on a still picture, so the menu is redrawn often enough. The decisions are in
`quickmenu_logic.h`, tested on a PC.

Colour themes: `src/gui/theme.c` holds five palettes (`k_themes`); `theme_select()` copies one into
`th_pal`, which the theme-dependent `TH_*` colours read, and loads its background
(`assets/bg_<theme>.png`, drawn by `tools/make_background.py`). Colours that carry a meaning (OK,
warning, error, the PlayStation symbols) are the same in every theme.

## Data on the memory card

The data folder is the first that can be created among `ux0:data/lune`, `ux0:lune` and
`uma0:data/lune` (`src/check_dir.c`; the name comes from `src/app_info.h`). It is not shared with
Moonlight, which keeps `ux0:data/moonlight`.

| Path | Content |
|---|---|
| `lune.conf` | settings (`src/config.c`); unknown keys are ignored, out-of-range values reset |
| `<PC name>/` | per PC: client certificate and key, unique ID, `device.ini` (addresses, MAC, paired) |
| `stats/session-<date>.csv`, `.txt` | per stream: one line per second, settings and percentiles |
| `stats/last_<app>.txt` | figures of the last session of each game, for the library |
| `boxart/<PC>/<app>.cover` | cover art, resized for the library |
| `lune.log`, `lune.1.log` .. `lune.4.log` | the log of this run and of the four before (`src/log.c`) |

## Log

`src/log.c` writes `lune.log` in the data folder on every run; the previous four runs are kept as
`lune.1.log` (newest) to `lune.4.log`. A line reads `14:03:27.512 I stream  started in 412 ms`: local
time (to match the PC's Sunshine log), level (E error, W warning, I information, D detail), subject.

- **Normal log** (always): start-up (version, firmware, model, free memory, battery, Wi-Fi), each PC
  contacted (Sunshine version, GPU, pairing, running game, codecs), each stream (settings, each start
  stage with its time, video, audio and controller set-up, how it ended and after how long),
  reconnections, pause and quick menu, errors, moonlight-common-c's own messages, and one *health* line
  per minute of play (frames, losses, bitrate, ping, PC, decode and display times, sound gaps, Wi-Fi).
  By design a start-up and a ten-minute game come to about a hundred lines (not yet measured on a Vita).
- **Detailed log** (*Settings > General > Detailed log*): every debug line of the code and of the
  HTTP requests (their query, which holds the stream key, is never written).

Callers format the line under a lightweight lock and copy it into a 64 KiB ring (`log_core.c`); the
low-priority `log_writer` thread puts the ring on the card once a second, at once after an error, and
reopens the file if a sleep closed it. No stream thread waits for the memory card. Floods are bounded:
the same line repeated is written once and then counted; each kind of line has a token bucket (a burst,
then a few lines a second; moonlight-common-c's loss messages 3 a second), and the next line written
says how many were left out; a full ring drops whole lines and says so; a file stops at 4 MiB.
